先打开 [离线对照板](board.html)。可以选择参考图、载入自己的新截图，在同一页比较。图片保存在 `images/`，无需访问原站；[sources.json](sources.json) 保存来源、发布日期、截图方式、原始尺寸和校验值。原图仅供设计研究，品牌和产品内容归原权利人，勿作为 O Chat 发布素材。

### P01 · 内容多，职责仍可辨认

[官方来源：How we redesigned the Linear UI](https://linear.app/now/how-we-redesigned-the-linear-ui)，2024-03-28。采用文中的 After 图，不采用 Concept 图。

观察主内容与左侧列表的边界、选中行和垂直对齐。O Chat 应让导航服务当前会话；只有相关任务确实需要时才出现额外面板。不要把图中三栏当作固定模板，也不要用它证明今天的 Linear 行为。

对比问题：视线能否自然从当前会话落到任务内容？侧栏宽度是否服务实际内容？

### P02 · 让当前项比背景导航更明确

[官方来源：A calmer interface for a product in motion](https://linear.app/now/behind-the-latest-design-refresh)，2026-03-12。图右为更新后的导航。

观察选中项与非活动项的重量差、统一的图标尺度和组间留白。迁移的是层级；O Chat 保持自己的浅色表面，并实测文字对比度。缩小图标不能代替足够的点击区域。

对比问题：当前 Agent / 会话是否一眼可辨？多种底色、描边和重复头像是否同时争夺注意？

### P03 · 容器边界要解释内容关系

与 P02 同源。原文说明图左采用更新后的分隔处理；这是一张重叠的局部展示图。

观察列表与工具栏如何分组，以及哪些边界更轻。O Chat 的每条线都应有职责：划分导航、正文、输入、审批等。审批后果与权限必须明确；不要为了清爽而去掉必要标签或焦点轮廓。

对比问题：拿走卡片外框后，内容关系是否仍然清楚？一组信息是否被重复边框拆散？

### P04 · 过程附着于工作，结果有具体名称

[官方来源：Raycast AI](https://www.raycast.com/core-features/ai)，抓取当日的页面。截图包含站点导航和演示边框；只研究中央聊天区域。

工具活动是一行摘要，回答有独立的阅读空间，最后出现有编号的产物。O Chat 可学习“过程 → 结果”的重量关系。有真实产物时呈现名称及可执行的下一步；没有真实链接或文件数据时，不制造下载按钮。

对比问题：用户先看到完成了什么，还是多处完成状态？结果是否足够具体？这张理想短对话不能替代长日志、失败或审批验证。

### P05 · 让目录条目足以支持选择

[官方来源：Raycast Store](https://www.raycast.com/store)。截图位于扩展目录，非页面顶部的大幅宣传区。

观察统一的名称、功能说明、来源信息和行动位置。O Chat 应用真实能力、输入与输出帮助用户选择，并明确在线与访问权的区别。不要照搬安装文案、下载次数或截断关键限制。

对比问题：两条 Agent 记录能否按同样的字段比较？用户是否明白选中后会做什么？

### P06 · 输入和运行控制形成有意义的组

[官方来源：Notion 3.2](https://www.notion.com/releases/2026-01-20)，2026-01-20。

观察输入内容与辅助工具的分组、发送行动，以及录音状态旁明确的停止控制。它是放大且裁切的宣传图；设备框、蓝色背景和物理像素都不适合作为 O Chat 的尺寸规范。

对比问题：输入、附件、发送、录音状态是否各有清楚位置？权限和退出操作能否被理解？这张图不能用于评判整屏手机阅读空间。

## 使用边界

- 开始修改前读 [比较方法](comparison.md)，选择最贴近当前状态的 1–2 个参考并查看图片。
- 目前有完整桌面参考；**尚无完整手机聊天、待审批、错误或恢复流程的外部参考**。这些状态继续使用 O Chat 标准与真实浏览器检查，若要宣称达到外部参考水准，需要补充匹配证据。
- 公共页面的标题叙事与产品演示参考由相邻的 `web-page-design/references/` 管理；不要搬进聊天工作区。
- 每次宣称改善都要附新截图和剩余差距。功能验收、参考比较、独立 AI 设计批评是不同的证据。
- 库中图片已实际打开审阅。新增图也必须做到这一点：不收只有链接、概念海报或看不清正文的缩略图。
