# 用参考图推动修改

## 开始设计前

1. 写清楚用户此刻的任务、必须读到的内容、下一步和关键状态。例如“手机上检查长任务的结果，同时知道仍处于 Full access”。
2. 从索引选择 1–2 张相近任务的图，并实际打开。先用完整界面判断构图；局部图仅回答局部问题。资料不足时明确缺口，必要时找新的官方截图。
3. 写一个可观察的目标：例如“已完成的过程成为附属摘要，结果标题、真实产物和下一步形成主阅读区”。“更高级”“像 Linear”不可直接验收。
4. 说明哪些做法适用于 O Chat、哪些因品牌、平台、内容或权限而不同。保留 OpenOnion 的标志与语义色。

## 截图后必须回答的三件事

| 问题 | 需要的证据 | 可接受的回答 |
| --- | --- | --- |
| 有没有达到相同或类似的效果？ | 参考中的视觉机制与本次截图对应区域 | 达到 / 部分达到 / 未达到，说明哪里 |
| 有没有达到相关的完成度？ | 层级、对齐、文字、空间、结果、行动在真实状态下的表现 | 仅对当前状态作判断；证据不足写无法判断 |
| 最大的差距在哪里？ | 具体区域、用户代价、下一次改动与复验状态 | 按影响排序，先修最大的 3 个，再截图 |

拒绝“留白更多所以更好”的推理。空白可以保护阅读，也可以暴露结果没有内容。拒绝只凭图标、圆角或颜色相似而通过。禁止数值总分掩盖关键问题。

第二问必须分清局部与整屏。对于未被本库覆盖的完整手机长结果、审批或错误状态，整屏外部比较结论必须写“无法判断 / 证据不足”。桌面短对话加手机输入裁图不能拼成完整手机参考；仍可按 O Chat 产品标准继续改进和验证。

## 看图顺序

1. **注意力**：先看到的是任务、结果、决策，还是外围状态与装饰？
2. **实质**：是否知道是谁、能做什么、已经得到什么、下一步是什么？只展示“完成”不等于呈现了结果。
3. **空间**：固定顶栏、底栏和展开面板用了多少真实视口？正文可连续阅读吗？新增空白是否来自隐藏必需信息？
4. **关系**：导航、过程、结果和输入是否能分开理解？重复状态、卡套卡、反复分隔是否破坏连续性？
5. **细节**：对齐基线、行距、换行、截断、图标大小与标签是否一致？先解决上述结构问题，再做细节。
6. **状态**：长标题、长回复、多步工具、流式增长、审批、失败、离线和触屏是否破坏同一层级？参考没有展示的状态不能默认合格。

## 比较应公平

- O Chat 的 before/after 必须是相同任务数据、相同宽高、缩放、滚动位置和可比状态，记录 build / commit。不要拿修复后的短内容比较旧版的长内容。
- 外部图通常无法取得同任务数据。记录它的主题、设备框、裁切和理想内容差异，只比较能够支持的构图关系；这是类比证据，不是控制实验。
- 查看完整原图与本地 100% 截图。对照板会等比缩放，且两个产品的逻辑像素不同，不能从看板缩略图推断字号、间距或点击区域。
- 浅色 O Chat 对暗色参考，比较视觉角色而非色值。对比度和触控尺寸必须在自己的实际 DOM / 浏览器中测量。
- 手机必须检查真实高度，至少覆盖项目要求的常用宽度和小屏长内容。P06 的输入区裁图不能作为整屏手机参考。

## 独立批评与收敛

把 O Chat 截图、参考图、用户任务、状态、尺寸和限制交给独立 AI 审阅者，要求先找最大的问题，并给 pass / revise 及证据。不要把作者的“已达标”作为审阅前提。

按最高影响问题修改，再用相同内容截图、送回复审。保留“批评 → 修改 → 新证据 → 结论”。存在拥挤、结果不可辨、必需决策被隐藏等重要问题时，结论为 revise；未获得充分截图或交互证据时，结论为 pending。一次 pass 只覆盖列出的状态，后续迭代仍需再审。

在项目文档中保存当前版本的差距清单；不要把会过时的缺陷写成永久风格。用相邻 `frontend-ui-verify/references/visual-review-record.md` 记录证据与独立的功能、设计结论。

## 维护参考库

新增参考时保存可辨认的图片、官方页面、原始图片 URL 或浏览器捕获方式、发布日期（未知则写未知）、抓取日期、图片尺寸和 sha256；标明真实网页、官方演示、局部宣传图或概念图。打开图片确认，不根据品牌知名度入选。

优先填补当前任务的证据缺口，而不是不断增加类似的漂亮图。换图时重新审阅其适用范围，更新 `sources.json`、索引与对照板。历史版本可以继续研究，但必须保留其日期；不要暗示它就是现行产品界面。
